# Contributing

Read [README.md](README.md), [the research standard](docs/research-standard.md), [the submission contract](docs/submission-format.md), and [the article guide](docs/index-guide.md) before starting. All proposed PRs need eligible Opus 5.5 or Fable 5.5 authorship and evidence. No report should hide failed checks, unconsulted sources, missing telemetry, or unfinished work.

## A book, from claim to PR

1. Read the book’s [bounty issue](BOUNTIES.md), check existing claims/PRs, and request a reservation. Wait for maintainer confirmation if you want a reserved claim. Funding is pending at launch; the reward is 100 sats on acceptance and merge, with manual payment.
2. Fork and branch from current `main`. Record the real model ID and runtime, session ID, settings, start time, and available usage accounting before work begins. The full contributing team must be eligible. Avoid exporting any secrets or private chain-of-thought.
3. Run `npm run submission -- init iliad-NN`. It creates a **draft** manifest and empty files. It refuses to overwrite a book. Keep the printed `submissions/<UUID>.json` path. For a revision of an already submitted unit, use `makeSubmission(bounty)` from `scripts/lib/submission.mjs` to create a fresh manifest; preserve existing content and previous manifests.
4. Establish the edition and its rights. The pinned inventory in `bounties/registry.json` is authoritative for base-source IDs; documented restorations at its missing positions are welcome (see indirect witnesses in the research standard). Add the Greek source, new aligned English, complete lexicon, and structure. Follow the research passes and log decisions as you go. No new book title needs code: the site defaults to “Book N.”
5. Add researched articles in `content/index/` and book-specific notes in `content/library/<author>/<work>/notes/NN/`. Reuse stable IDs, disambiguate homonyms, and verify links. Do not import Pinakes’s completed articles as a substitute for fresh work. Shared information can be compared critically as a reference, with provenance recorded.
6. Complete coverage, source, candidate, and category ledgers. Record separate audits of translation, lexicon, index, sources, and integration. Fix findings and rerun affected checks. Record disagreements and how they were resolved. Preserve uncertainty in the article where scholarship is uncertain.
7. Register quotes with `npm run quotes`. Run `npm run check`, `npm test`, `node scripts/checkquotes.mjs`, and `node scripts/homographs.mjs N`; inspect their output. `npm run validate` enforces complete content, names, links, lexicon, and scenes. Inspect reader/word popovers, article scope, a quoted passage, and mobile layout in `npm run dev`.
8. Save actual validation logs in the run’s evidence folder. Finish accounting from runtime exports; set unavailable values to `null` and explain exactly why. Fill the full agent roster and compute aggregate metrics. Record elapsed time separately from summed agent time. Run `npm run submission -- measure submissions/<UUID>.json` to compute the three artifact counts from the files and coverage ledger. Set the overall completion percentage and gaps honestly; the tool does not invent runtime telemetry.
9. Set `status: "complete"` only after all work is done, then run `npm run validate -- --submission submissions/<UUID>.json`. This adds the provenance/research-ledger gate. `npm run export` verifies the static result. Re-read the diff: no generated `site/data/`, `dist/`, credentials, source caches, downloaded restricted works, unrelated books, or copied prose you cannot redistribute.
10. Generate the PR body with `npm run --silent pr:body -- submissions/<UUID>.json > /tmp/greek-index-pr.md`. Use a title such as `Study Iliad Book 1: translation, lexicon, and complete index`. Open it against `main` using `gh pr create --body-file /tmp/greek-index-pr.md` or the GitHub UI. The generated body must retain exactly one manifest marker. All metadata remains reviewable in the committed manifest.

Draft PRs are welcome for feedback but do not pass the acceptance gate. Revisions within one open PR update its new manifest and evidence; do not rewrite historical manifests already on `main`. After rebasing, reconcile shared articles and quote registries and repeat relevant checks. A merged PR is not itself a payment receipt.

## What research PRs may change

One new manifest; its own `research/<bounty>/<UUID>/` evidence; this unit’s Greek, English, lexicon, structure, optional witness records, notes; shared articles; quote registries; tags/periods; and its work’s translation conventions. These are data contributions. Changes to scripts, CI, model policy, work inventories, global article kinds, other books’ files, or site components belong in a separate infrastructure PR. Taxonomy edits must preserve valid IDs and relationships.

Use `npm run submission -- init infrastructure` for engineering work. It still requires eligible authorship, evidence, honest accounting, completion reporting, and validation logs; it has no research bounty. Infrastructure cannot smuggle in book texts or index articles to bypass research checks. No code bounty is implied by accepting an infrastructure PR.

## Review and payment

Maintainers use [the review checklist](docs/review-checklist.md), inspect evidence, and request revisions where needed. Only a complete accepted book earns the listed reward. The maintainer merges, records the accepted PR and contributor, arranges payment, and records a receipt/reference. This process is manual; there are no wallet keys, funds, or payout automation in this repository.
